# 正式入库执行说明

## 入库顺序
1. 使用 `01_global_rag_ingest_manifest.dedup.jsonl` 作为唯一输入清单（禁止使用原始 manifest 直导）。
2. 先导入 Markdown 文档（`03_markdown_docs_ingest_list.md` 对应路径）。
3. 再导入源码与配置类文档（按 collection 分组 JSONL）。

## collection 说明
- `ztgame_server_core`：核心服务、网关、场景、角色流程。
- `ztgame_server_config`：配置、参数、表结构与加载逻辑。
- `ztgame_server_script_quest`：Lua 与任务脚本相关资料。
- `ztgame_server_tools_ops`：运维工具、脚本、管理流程。
- `ztgame_server_risk`：风险事项、高危变更、误操作防护。
- `unknown_collection`：仅在出现未知 collection 时使用，需人工复核后再导入。

## metadata 字段
建议至少保留：`path,module,level,domain,recommended_collection,chunk_hint,keywords,reason`。

## chunk 切片规则
- Markdown：按标题层级（H1/H2/H3）优先切片，目标 300~800 中文字/块。
- 源码：按函数/逻辑段切片，建议 80~200 行/块；保留文件路径与行号元数据。
- 表格/清单：整表同块，避免拆散字段语义。

## 去重策略
- 主键：`(path, module, level)`。
- 保留首次出现记录，后续重复记录丢弃并记录于 `02_manifest_dedup_report.md`。

## 失败回滚策略
1. 按 collection 分批导入并记录批次号。
2. 任一批失败，仅回滚失败批次数据（按 `ingest_batch_id` 或导入时间窗口删除）。
3. 回滚后先修复数据，再重试该批，不影响已成功批次。

## 导入后抽样检查
- 每个 collection 至少抽样 5 条向量记录，核对 `path/module/level`。
- 对 11 类标准问答（见 `06_rag_qa_eval_template.md`）做首轮召回验证。
- 若召回偏差 >20%，优先检查 chunk 策略与 metadata 丢失。
