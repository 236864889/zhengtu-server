# 教程系列 + 官网 + 登录器 + MySQL 治理执行计划（30天）

> 目标：把前两份“盘点/深度分析”转为可执行项目计划，直接用于排期与验收。

## 1. 执行总览

- 周期：30 天
- 分期：P0（第1周） / P1（第2-3周） / P2（第4周）
- 牵头角色：
  - 技术负责人（总控）
  - PHP/官网工程师
  - 登录器工程师
  - DBA
  - 测试与运维

## 2. P0（第1周）：安全止血与交易可用性保障

## 2.1 下线明文凭据（D1-D2）

### 动作
1. 轮换数据库账号密码。
2. `db.php` 改为读取环境变量（保留本地开发模板文件，不入库）。
3. 全站检查 `DB_`、`PASS`、`KEY` 等敏感常量是否落盘。

### 交付物
- `db.php` 无明文生产凭据。
- `.env.example`（或等效模板）
- 安全变更记录（轮换时间、影响范围、回滚方式）

### 验收标准
- 仓库内不再出现生产凭据。
- 官网功能（注册/充值/抽奖/找回）全链可用。

## 2.2 支付回调验签回归（D2-D3）

### 动作
1. 把 `epay_notify.php` 的签名算法与时窗校验写成测试样例。
2. 准备三类回调包：正确签名 / 错误签名 / 超时回调。
3. 验证幂等：同一订单重复回调，资金只入账一次。

### 交付物
- `tests/payment_notify_cases.md`（或同类文档）
- 可复用请求脚本（curl 或 Postman 集）

### 验收标准
- 正确回调返回 success。
- 错签返回 sign_error。
- 超时回调返回 timeout。
- 重复回调不重复加点。

## 2.3 密码存储策略核验（D3-D5）

### 动作
1. 对 `ACCSTORE0000.PASSWD` 做样本检查（现网/测试库）。
2. 核对游戏服务端登录验证逻辑是否要求明文或特定哈希。
3. 形成“可迁移”方案：旧口令兼容 + 新口令策略。

### 交付物
- 《账号口令机制核验报告》
- 若可改：迁移脚本与灰度策略

### 验收标准
- 明确当前口令方案真实形态（明文/摘要/混合）。
- 明确是否可迁移及风险边界。

---

## 3. P1（第2-3周）：稳定性与可维护性提升

## 3.1 字符集统一蓝图（W2）

### 动作
1. 梳理所有连接与表字段编码（latin1/gbk/utf8mb4）。
2. 标注边界转换点（仅在 IO 边界做转换）。
3. 先出“冻结策略”：新字段统一 utf8mb4，旧字段不强迁。

### 交付物
- 《字符集与排序规则矩阵》
- 《编码转换边界清单》

### 验收标准
- 新功能禁止新增混用编码。
- 抽奖与账号链路不再新增乱码反馈。

## 3.2 官网公共层抽离（W2-W3）

### 动作
1. 抽离 DB 连接、统一响应、日志脱敏、限流为公共组件。
2. 注册、找回、充值、抽奖接入公共层。
3. 增加统一错误码与错误文案表。

### 交付物
- `lib/`（或等价目录）
- 《官网错误码清单》

### 验收标准
- 重复代码显著减少。
- 关键入口（注册/充值回调/抽奖）都走统一安全基建。

## 3.3 登录器分层改造（W3）

### 动作
1. `Form1.cs` 分拆为：UI层 / 配置拉取层 / 更新执行层。
2. 增加 JSON 拉取失败降级策略（本地缓存配置）。
3. 清理 `bin/obj` 入库文件并完善 `.gitignore`。

### 交付物
- 登录器分层设计说明
- 降级机制实现说明

### 验收标准
- JSON服务短时不可用时，登录器可显示可用提示并降级运行。
- 代码可读性与模块边界提升。

## 4. P2（第4周）：知识资产工程化

### 动作

## 5. 风险与回滚策略

1. **账号/支付变更风险最高**：任何变更均先在测试库联调。
2. **编码迁移禁止“一步到位”**：先冻结新增，再渐进治理。
3. **登录器配置中心单点风险**：必须保留本地缓存降级。
4. **教程重写风险**：必须保留“原文链接 + 重写版本号”。

---

## 6. 里程碑与度量指标（KPI）

- M1（第7天）：凭据下线 + 支付验签回归完成。
- M2（第21天）：官网公共层落地 + 登录器分层初版。
- M3（第30天）：SOP手册首批完成 + E2E发布清单启用。

建议量化指标：

- 安全：仓库敏感信息扫描命中数 = 0
- 稳定：充值漏单率 = 0（以对账为准）
- 质量：教程重复主题占比下降 > 40%
- 交付：发布前E2E清单执行率 = 100%
