## 1. 范围与方法

本次分析覆盖四个资产域：

1. `教程系列_上传版`
2. `配套官网`
3. `登录器`
4. `mysql`

分析方法：

- 目录/扩展名统计（看规模与形态）
- 关键入口文件走读（看职责与调用链）
- 识别跨目录耦合（账号、充值、积分、抽奖、区服）
- 给出可落地的重构优先级

## 3. 教程系列（`教程系列_上传版`）深度结论

## 3.1 目录职能分层

- `服务端说明`：任务/NPC/技能/TBL/编译部署等“直接改服”知识。
- `客户端说明`：PAK/TBL、贴图/称号/特效等“表现层资源改造”。
- `网络收集教程`：社区转载与工具打包区，覆盖广但质量差异大。

## 3.2 资料质量画像

- 优点：覆盖“从部署到玩法改造”的完整面，适合老版本快速上手。
- 痛点：
  - 重复主题多（同名/近义文档跨目录出现）。
  - 版本边界弱（Win1.1、1.10、7.x 混杂）。
  - 文件命名不规范（如“新建 文本文档*.txt”）。

## 3.3 对工程化落地的价值

教程系列不是“现行规范文档”，更像“经验素材池”。
建议角色定位：

- **输入层**：用于抽取操作步骤、字段说明、排障套路。
- **非真相源**：最终以代码与SQL为准，不直接当权威规范。

## 4. 配套官网（`配套官网`）深度分析

## 4.1 功能版图

从入口文件可识别 5 条主业务线：

1. 注册与邮箱验证码：`register_compat.php`、`reset_password_backend.php`
2. 充值下单与回调：`recharge_compat.php`、`epay_notify.php`
3. 抽奖系统：`lottery.php`、`lottery_draw.php`、`lottery_recent.php`、`lottery_pool_5000.sql`
4. 账号辅助：`balance_query.php`、`cdk_recharge.php`
5. 安全与基建：`security_bootstrap.php`、`rate_limit.php`、`db.php`

## 4.2 安全性与风险点（关键）

### A. 明文凭据暴露风险（高危）

`db.php` 内存在硬编码数据库主机/账号/密码，且仓库可见。该问题在任何公开/多人分发场景都属于高危泄露点。

### B. 字符集策略不一致（高风险）

- `db.php`/部分连接使用 `latin1`
- `reset_password_backend.php` 连接使用 `utf8mb4`
- `lottery_draw.php` 手动 `SET NAMES latin1` 并做 `GBK<->UTF-8` 转换

这说明系统处于“历史库编码兼容模式”，维护难点是：新增字段/新功能极易出现乱码或比较异常。

### C. 密码处理可疑（高风险）

`reset_password_backend.php` 直接更新 `ACCSTORE0000.PASSWD`，未见标准哈希流程（需与游戏登录验证端再次核对）。如果真实使用明文/弱散列，将带来严重账号安全风险。

### D. 回调签名与时效校验（中高）

`epay_notify.php` 已有签名比对、5分钟时窗与幂等处理，这是亮点；但依赖配置项与上游协议完全一致，一旦签名风格变更容易导致漏单/拒单。

## 4.3 架构形态判断

官网是“**PHP脚本聚合型单体**”：

- 优点：部署简单、改动快。
- 缺点：配置散落、复用弱、测试体系弱、变更容易互相影响。

## 5. 登录器（`登录器`）深度分析

## 5.1 启动与核心流程

`Program.cs` 流程清晰：启用UI样式 -> 浏览器兼容设置 -> 启动主窗体 `title`。

`Form1.cs`（`title`）承担了多职责：

- 拉取远程 JSON（区服列表 + 页面链接 + 更新配置）
- 区服树展示与选择
- 自更新（登录器自身）
- 游戏文件更新
- 写 `config.ini`
- 启动游戏进程
- 自动创建桌面快捷方式

这是典型“胖客户端启动器”。

## 5.2 关键耦合点

1. **远程配置中心耦合**：`JSON_URL` 固定指向外部地址，地址失效会导致初始化失败。
2. **站点入口耦合**：官网/注册/充值/抽奖/找回密码链接都由 JSON 下发，利于运营切换，但提高了配置正确性要求。
3. **补丁分发耦合**：更新项包含 `RelPath/Md5/Url`，若 CDN、MD5 或压缩包结构不一致，会直接影响启动体验。

## 5.3 工程治理问题

- 仓库包含 `bin/obj` 中间产物，建议清理并补 `.gitignore`。
- UI事件与网络/IO/更新逻辑耦合在一个窗体类，长期迭代成本高。

## 6. MySQL 目录（`mysql`）深度分析

`mysql` 虽小，但是所有系统的事实底座：

- `FLServerDB.sql`：账号、积分、充值、日志等高频业务核心库。
- `ZtGameDB.sql`：游戏侧数据域（角色/玩法等，需结合服务端代码映射）。

结合官网代码可确认高频表包括：

- `ACCSTORE0000`（账号主表）
- `POINTBONUS0000`（点数）
- `RECHARGEORDERS`（充值订单）
- `CONSUMELOG0000`（资金/点数流水）
- `REG_EMAIL_CODE`（验证码与限流依据）
- `LOTTERY_POOL` / `LOTTERY_LOG`（抽奖系统）

结论：MySQL目录虽文件少，但其变更风险最高（影响官网、登录器联动、游戏计费与账号可用性）。

---

## 7. 四域联动关系（最关键）

1. 教程系列给出“经验操作”
2. 官网实现“账号注册/充值/找回/抽奖”
3. 登录器承接“入口/公告/区服/更新”
4. MySQL承接“账号与资金事实数据”

可抽象为一条主链：

**玩家入口（登录器） -> 官网动作（注册/充值/抽奖） -> 数据落库（MySQL） -> 游戏消费与校验（服务端）**

任何单点改动（尤其表结构、字段编码、签名算法）都可能引发整链故障。

## 8. 深度整改建议（按优先级）

## P0（立即）

1. 移除仓库中的明文数据库/支付敏感配置，改为环境变量或独立未入库配置。
2. 对账号密码存储策略做一次“代码 + 数据库 + 登录验证端”全链核验。
3. 固化充值签名协议文档与回调验签测试样例，防止支付参数漂移。

## P1（短期）

1. 统一字符集策略（至少先定义“库层编码准则 + 边界转换点”）。
2. 拆分官网公共层（DB连接、鉴权、限流、响应）减少重复逻辑。
3. 登录器拆分：UI层 / 配置拉取层 / 更新执行层。

## P2（中期）

1. 把教程系列抽取为“标准操作手册（SOP）+版本前提+风险回滚模板”。
2. 建立表结构版本化（migration）与灰度验证流程。
3. 建立端到端联调清单：注册->登录->充值->到账->抽奖->日志对账。

---

## 9. 最终结论

- 该仓库不是单一项目，而是“历史教程资产 + 官网业务 + 客户端启动器 + 数据底座脚本”的复合交付包。
- 当前最大问题不是“功能缺失”，而是“知识分散、配置暴露、编码混用、跨域变更缺乏统一治理”。
- 若目标是长期稳定运营，优先顺序应是：**安全合规 -> 数据一致性 -> 联动可观测 -> 教程工程化沉淀**。
