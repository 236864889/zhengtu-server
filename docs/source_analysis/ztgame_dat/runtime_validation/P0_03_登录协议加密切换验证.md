# P0-03 登录协议加密切换验证

## 1. 验证目标

本阶段基于静态源码确认 ztgame.dat 客户端在“登录 UI -> 登录服 -> 登录成功 -> 二跳游戏服 -> 版本验证 -> 选角/进场景”链路中的协议与加密切换机制，重点核实：

- 登录点击后如何发起连接与登录命令；
- `CClient::Connect` 的调用路径；
- 登录包组包与发送入口；
- 登录阶段 RC5 / 会话阶段 DES 的切换时机；
- `m_bLoginRecv` / `m_bLoginSend` 与 key 状态变化；
- `stServerReturnLoginSuccessCmd` 的处理和二跳地址来源；
- `stUserVerifyVerCmd`、`stLoginSelectUserCmd` 在流程中的发送时机。

## 3. 登录协议总流程图

按当前源码实际顺序，登录主链如下：

1. 登录界面按钮点击（`CGuiLogin::OnGuiEvent`，按钮 ID=5）
2. 读取账号/密码（编辑框 3/4）+ 验证非空，调用 `LoginGame(...)`
3. 客户端已在 `InitGame -> ConnectionLoginServer` 阶段连接登录服并先发 `stUserVerifyVerCmd`
4. 登录服交互阶段使用 RC5（`m_bLoginSend=true` / `m_bLoginRecv=true`）
5. 若收到 `SERVER_RETURN_LOGIN_OK`，`ParseLoginMessage` 调 `CNetAutoConnect::LoginGameServer`
6. 读取登录成功包中的 `pstrIP` / `wdPort` / `key+keyOffset`
7. `___ConnectToGameServer` 先 `GetClient()->Destroy()` 断旧连接，再 `Connect(pstrIP, wdPort)` 二跳
8. 用登录成功包 key 派生 DES key（8 字节）写入 `m_key`
9. 发送到游戏服：`stUserVerifyVerCmd` -> `stPasswdLogonUserCmd`
10. 发送完二跳登录包后，将 `m_bLoginSend=false`（发送侧切换到 DES）
11. 同时 `m_bLoginRecv=false`（接收侧切换到 DES）
12. 进入选角界面后发送 `stLoginSelectUserCmd`，成功后进入场景初始化/`StartGame`

## 4. 登录 UI 到 CClient::Connect 调用链

| 顺序 | 调用/事件 | 源码文件 | 函数 | 作用 | 备注 |
|---|---|---|---|---|---|
| 1 | 登录按钮点击(ID=5) | `Client/GuiLogin.cpp` | `CGuiLogin::OnGuiEvent` | 读取账号/密码，调用 `LoginGame` | 输入为空会直接返回，不发包 |
| 2 | 客户端启动时登录服连接 | `Client/Game.cpp` | `InitGame -> ConnectionLoginServer` | 从配置地址列表逐个尝试连接 | `GetConfig()->szLoginAddress/szLoginPort` |
| 3 | 建连实现 | `Client/Client.cpp` | `CClient::Connect` | TCP 连接成功后启动 `Client_MsgThread` | 所有连接（首跳/二跳）都走这里 |
| 4 | 登录成功后二跳连接 | `Client/NetAutoConnect.cpp` | `___ConnectToGameServer` | 断开旧连接并连接 `stServerReturnLoginSuccessCmd` 下发地址 | `pstrIP` / `wdPort` 来自登录成功包 |

重点结论：

- **登录按钮本身不直接调用 `Connect`**，而是调用 `LoginGame` 发登录指令；登录服连接在 `InitGame` 期间已完成。  
- 登录服 IP/Port 首跳来源于配置对象（实质由 `config.ini` 读入到 `m_Config` 后使用）；命令行覆盖逻辑不在本次目标文件中展开，但连接函数使用的是 `GetGameApplication()->GetConfig()` 当前值。  
- 存在自动重连/自动进入分支：`CNetAutoConnect::TryBeginAutoConnect` / `AutoEnterGS`。

## 5. 登录包组包与发送入口

### 5.1 登录相关结构

- 首跳登录请求：`stUserRequestLoginCmd`（账号、密码、`game`、`zone`、`jpegPassport`、`mac_addr`）
- 版本验证：`stUserVerifyVerCmd`（`version`）
- 登录成功回包：`stServerReturnLoginSuccessCmd`（`pstrIP`、`wdPort`、`key/keyOffset`、`dwUserID`、`loginTempID`）
- 二跳登录包：`stPasswdLogonUserCmd`（`dwUserID`、`loginTempID`、账号密码）
- 选角包：`stLoginSelectUserCmd`（`charNo`）

### 5.2 发送链

业务命令统一走：

`SEND_USER_CMD / Client_SendCommand 宏 -> GetClient()->Send(...) -> CClient::Send`。

`CClient::Send` 会：

1. 计算长度并按需压缩；
2. 写长度头并设置 `PACKET_FLAG_ENC`（以及必要时 `PACKET_FLAG_ZIP`）；
3. 根据 `m_bLoginSend` 选择 RC5 或 DES 加密；
4. 最终调用 socket 发送。

## 6. RC5 登录阶段分析

### 6.1 初始状态

- `CClient` 构造中：`m_bLoginRecv = true`、`m_bLoginSend = true`
- `InitGame(bConnServer=true)` 再次显式置为 `true/true`

即：首跳登录阶段收发默认均走 RC5。

### 6.2 RC5 调用点

- 接收线程 `Client_MsgThread`：`if(m_bLoginRecv) RC5_32_decrypt(...)`
- 发送流程 `CClient::Send`：`if(m_bLoginSend) RC5_32_encrypt(...)`

### 6.3 包头/标记

- 封包长度类型 `tPackLengthType`
- 标记位：
  - `PACKET_FLAG_ENC = 0x80000000`
  - `PACKET_FLAG_ZIP = 0x40000000`
- 接收侧先按 8 字节块解密，再按长度/标记解包（含可选解压）。

结论：登录阶段启用 RC5 是由 `m_bLoginRecv/m_bLoginSend` 状态位驱动，而非按 cmd id 白名单切换。

## 7. DES 会话阶段分析

### 7.1 DES key 来源

`stServerReturnLoginSuccessCmd` 内含 `key[256]` 与 `keyOffset`。客户端在 `___ConnectToGameServer` 中执行：

- `BYTE* pKeyData = &cmd->key[cmd->keyOffset];`
- `Client_SetKey(GetClient()->m_key,pKeyData,8);`

即从下发 key 池偏移处取 8 字节作为 DES 会话 key。

### 7.2 切换时机

二跳连接成功后：

- `m_bLoginRecv = false`（接收改用 DES）
- 发送 `stUserVerifyVerCmd` + `stPasswdLogonUserCmd` 期间，`m_bLoginSend` 仍为 `true`（仍 RC5）
- 发送完 `stPasswdLogonUserCmd` 后：`m_bLoginSend = false`（发送改用 DES）

因此切换并非“同一时刻双向同时切”，而是：**先收切、后发切**。

## 8. 登录成功回包处理

### 8.1 `stServerReturnLoginSuccessCmd` 处理点

- `ParseLoginMessage` 收到 `SERVER_RETURN_LOGIN_OK` 后，调用：
  - `CNetAutoConnect::Instance()->LoginGameServer((stServerReturnLoginSuccessCmd*)pCmd)`
- `LoginGameServer` 先备份到 `m_BackCmd`，再执行 `___ConnectToGameServer`

### 8.2 二跳连接关键行为

`___ConnectToGameServer` 中：

1. `GetClient()->Destroy()`：断开旧连接并清理线程/缓冲；
2. `GetClient()->Connect(cmd->pstrIP, cmd->wdPort)`：连接新地址；
3. 从 `cmd->key/cmd->keyOffset` 设置 DES key；
4. 发送版本验证 + 二跳登录凭据。

结论：

- 登录成功后会断开首跳连接并重连；
- 二跳 IP/Port 来自 **登录成功包下发**（不是直接用 config.ini）；
- 语义上是由登录服引导到后续网关/游戏服节点。

## 9. 版本验证与进场景流程

### 9.1 `stUserVerifyVerCmd` 发送时机

有两处：

1. 首跳连接登录服成功后（`ConnectionLoginServer`）发送一次；
2. 二跳连接成功后（`___ConnectToGameServer`）再发送一次。

`version` 来源：

- `_AUTOPLAY` 下取 `GetGameVersion()`（来自 `config.ini` 的 `other.version`，并有下限修正）；
- 非 `_AUTOPLAY` 下默认 `ZTGAME_VERSION`；
- 代码中还存在 `cmd.version = 1999` 的硬编码覆盖（位于首跳 `ConnectionLoginServer`），需动态验证确认是否为调试遗留。

### 9.2 `stLoginSelectUserCmd` 发送与缓存

- 选角界面 `CGuiSelectCharDialog::LoginServer()` 发送 `stLoginSelectUserCmd`。
- 自动重连支持缓存：`CNetAutoConnect::BackUpLoginSelectCmd` 备份 `m_BackLoginCmd`，`AutoEnterGS` 可在重连后重发。

### 9.3 进入场景

选角成功后，流程进入场景初始化与 `StartGame`（关闭登录/选角 UI、启用主 UI、进入运行态）。

## 10. 客户端与服务端对应关系

> 当前仓未提供 `base/Command.h` 等 server 侧文件，以下为“客户端协议定义 vs 通用服务端实现期望”的静态对应。

| 客户端结构/函数 | 服务端对应结构/函数 | 关系 | 风险 |
|---|---|---|---|
| `stUserVerifyVerCmd.version` | 登录服版本校验命令 | 首跳/二跳均可能校验版本 | version 规则不一致会直接失败 |
| `stUserRequestLoginCmd` | 登录服账号认证命令 | 承载账号/密码/区服等字段 | 字段长度/顺序不一致会鉴权失败 |
| `stServerReturnLoginSuccessCmd` | 登录服登录成功回包 | 下发二跳 IP/Port、临时ID、key | `keyOffset`/key 解析错会导致后续解密失败 |
| `stPasswdLogonUserCmd` | 游戏服二次登录命令 | 带 `dwUserID/loginTempID` + 账号密码 | 任一字段错会导致“登录成功后二跳失败” |
| `stLoginSelectUserCmd` | 选角命令 | 选角色并进入地图链路 | `charNo` 或协议号错误会卡选角 |
| `CClient::Send/Client_MsgThread` | 服务端 packet pack/unpack | 双方需一致处理 `ENC/ZIP` 标记、8字节对齐 | 加密状态位与包头处理不一致会全链路不可用 |

---

## 11. 风险结论

以下项属于“高风险不可随意改动”：

1. 命令号与 `byCmd/byParam` 映射（登录、版本、选角相关）；
2. 协议字段顺序/长度（尤其账号密码、`dwUserID`、`loginTempID`、`pstrIP/wdPort`、key 区域）；
3. 包长度头与标记位处理（`PACKET_FLAG_ENC/ZIP`）；
4. 8 字节分组加解密前提；
5. `m_bLoginRecv/m_bLoginSend` 切换时序；
6. key 下发与 `keyOffset` 取值逻辑；
7. 登录成功后二跳地址使用逻辑；
8. `version` 计算/覆盖规则；
9. 选角命令缓存与断线重发逻辑。

## 12. 对 C# 登录器的影响

### 12.1 是否需要自己处理 RC5/DES？

常规外置 C# 登录器 **不需要** 直接处理游戏协议 RC5/DES。当前客户端已内置协议收发、RC5/DES 切换与 key 处理逻辑。

### 12.2 是否只负责写 config.ini + 启动客户端？

在当前架构下，**主要职责是**：

- 写入/维护 `config.ini`（账号记忆、区服、版本策略等）；
- 组织启动参数并拉起客户端进程；
- 展示错误信息与重试引导。

### 12.3 是否需要传命令行参数？

可选，需要结合现网客户端是否启用命令行覆盖配置逻辑。若已有命令行覆盖分支，登录器传参可减少改文件频率；否则以 `config.ini` 为主。

### 12.4 登录失败怎么区分？

建议按阶段分层判定：

1. **连接失败**：`Connect(login_ip,login_port)` 失败（首跳网络问题）；
2. **版本失败**：收到 `SERVER_RETURN_LOGIN_FAILED` 且 `byReturnCode = LOGIN_RETURN_VERSIONERROR`；
3. **账号失败**：`LOGIN_RETURN_PASSWORDERROR` / 锁定等账号类返回码；
4. **二跳失败**：已收到登录成功但 `Connect(pstrIP,wdPort)` 失败或后续二跳登录失败。

## 小结（P0-03 结论）

1. 登录协议是“首跳登录服 + 登录成功后二跳游戏服”的双连接模型。  
2. RC5 -> DES 切换由 `m_bLoginRecv/m_bLoginSend` 驱动，且是先收后发分步切换。  
3. 二跳 `IP/Port` 与 DES key 材料均来自 `stServerReturnLoginSuccessCmd`，不是 config.ini 直连。  
4. C# 登录器通常不需要自己实现 RC5/DES，重点在配置、启动与错误分层提示。  
5. 下一步优先进入“动态验证”阶段（建议按本文件第 13 节执行），再决定是否立项 P0-04。
