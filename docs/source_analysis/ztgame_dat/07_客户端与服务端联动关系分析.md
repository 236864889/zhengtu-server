# 客户端与服务端联动关系分析（Gateway/Session/Scenes/Command）

## 1. GameMain -> 窗口初始化 -> 登录界面 -> 网络连接链路
- 入口：`WinMain -> main -> CGameAppation::InitInstance`。
- 初始化：创建 `CGameScene`、`CClient`，加载 config 与 UI/资源。
- 登录：登录/选角 UI 组包（如 `stLoginSelectUserCmd`）并通过 `Client_SendCommand` 发出。
- 切服/入场：`NetAutoConnect::LoginGameServer` 接收登录成功回包后重连游戏服地址与端口，并发送版本与口令命令。

## 2. NetAutoConnect / Socket / Connect / IP / Port 来源
- `NetAutoConnect` 会读取/写入 `config.ini`（版本号等），并基于登录成功包中的 `pstrIP/wdPort` 调 `GetClient()->Connect`。
- 说明连接来源是“登录阶段下发 + 本地配置辅助”，而非完全硬编码。

## 3. OpenPackFileForRead 调用树（重点包）
- 已确认：
  - `datas.pak`：例如 `LoadFaceInfo` 读取 `datas\face.xml`。
  - `sound.pak`：`Media/SoundBufferDX.cpp` 加载音效数据。
- 推断：地图/场景/UI 其余 XML 与二进制资源也遵循相同 `OpenPackFileForRead` 接口，从不同 pack 文件分流。

## 4. miniusercommand.h 与服务端协议对应
- `Client/miniusercommand.h` 与 `base/MiniUserCommand.h` 在结构和 `subParam` 常量上基本同构（如 `LOGIN_COMMON_MINI_PARA=3`、`GAME_LIST_COMMON_MINI_PARA=5`）。
- 这说明 MiniGame 协议是“同一协议头 + 同一参数号”的双端共享模型；MiniServer/网关只做转发与分发时，需严格保持结构体字节布局一致（`#pragma pack(1)`）。

## 5. 客户端协议头与服务端 base/*Command.h 对应
- 客户端发包统一 `Client_SendCommand`，命令体继承 `stNullUserCmd`，字段含 `byCmd/byParam`。
- 服务端 `base/Command.h`、`base/MiniUserCommand.h` 以相同命令号体系定义解析结构，Scenes/Session/Gateway 各进程按命令类型分流处理。

## 6. 客户端连接哪个服务、登录后如何进场景
- 首跳：客户端先走登录链路，成功后拿到新的 IP/Port 与 key。
- 二跳：客户端重建 socket 连接到游戏服入口（通常网关或场景接入点），再完成用户验证与角色进入。
- 后续：场景行为类命令由 ScenesServer 消费，社交/跨场景能力由 SessionServer 等承接。

## 7. config.ini 与登录器区服写入关系
- `config.ini` 在客户端中确定可读写，已用于版本与自动连接辅助信息持久化。
- `servername/zone/loginaddress/loginport` 等字段若由外部登录器写入，客户端侧通常在启动/登录阶段读取并转为连接参数；具体字段名需结合登录器源码或发布脚本再做一跳核对。

## 8. EncDec / PakTest / execryptor 边界
- `EncDec`：网络包加解密（登录 RC5、会话 DES）与资源包加密能力（Pack flags）两条线。
- `PakTest`：偏离线解析/验证工具，可用于检查包结构与导出文件。
- `execryptor` 与 `CHECK_DEBUGGER*`：属于客户端保护/反调试相关边界，不直接等同协议加密；主要防护运行时与注入/调试风险。
