## 1. 工具职责边界（v1.2 新增）

### 1.1 Codex 可执行职责（仓库内静态工作）

- 仓库静态分析（文件结构、文本内容、依赖关系线索）。
- 文档修订与任务模板维护（`docs/operations/`）。
- 代码补丁建议（仅基于仓库证据，不宣称实机验证）。
- `Makefile` / shell 脚本文本核对（顺序、命令、风险点）。

### 1.2 Claw/SSH/人工职责（真实环境动作）

- 真实环境检查（系统依赖、磁盘、端口、进程、权限）。
- 实际编译与复验（如 `make -C base`、全量编译）。
- 启动/停服/联调（服务进程、端口监听、客户端登录链路）。
- 数据库可达性与真实数据校验。

### 1.3 明确禁止错配

- 不得要求 Codex 执行 `gcc --version`、`mysql_config --version`、`df -h`、`ss -lntp`、`make` 等真实环境测试或执行动作。
- 上述动作必须转交服务器侧 Claw/SSH/人工执行。

## 3. 编译链路（事实基线，仅记录不执行）

以 `ztgame/Makefile` 的 `SUB_DIRS` 为准：

`base/EncDec -> base -> MiniServer -> ScenesServer -> SessionServer -> BillServer -> GatewayServer -> SuperServer -> RecordServer -> FLServer -> tools`

补充说明：

- `script` 不是顶层 `SUB_DIRS`，但 `ScenesServer` 等模块会链接 `script/liblua.a`、`script/libluabind.a`、`script/liblualib.a` 等静态库。
- 编译产物核对重点：`libencdec.a`、`libzebra.a`、`libcrypto.a`、各 Server 二进制、`tools` 产物。
- 本手册只维护“编译顺序事实”，不在 Codex 环节执行编译。

## 4. 启动顺序双基线（事实并列，不混写）

### 基线A：`start.sh`

`Super -> Record -> Bill -> Mini -> Session -> Scenes -> Gateway`

- `FLServer` 默认注释，不启动。

### 基线B：`start1.sh`

`Super -> FL -> Record -> Bill -> Mini -> Session -> Scenes -> Gateway`

- `FLServer` 默认启动。

使用要求：

1. 上线前必须先确定正式 SOP 采用 A 还是 B。
2. 文档、脚本、值班手册必须保持同一基线。
3. Codex 仅可静态比对两份脚本文本，不可执行启动验证。

## 5. shebang 异常兼容说明（v1.2 新增）

- `start.sh` 与 `stop.sh` 首行 shebang 存在异常风险（如缺失 `#` 或顺序异常），可能导致脚本无法按预期直接执行。
- 若脚本不可直接执行，应采用显式方式：`bash ztgame/start.sh` 或 `bash ztgame/start1.sh`。
- 生产上线前，应由服务器环境确认最终脚本执行方式（直接执行或 `bash` 调用）。
- Codex 只能静态报告该风险，不能验证真实执行效果。

## 6. UserServer 状态说明（强化）

- 当前源码树内未见独立 `UserServer` 目录。
- `UserServer` 可能是历史术语、部署外部组件或旧版本组件。
- 是否为部署必需组件，必须由服务器部署实测或历史运维记录确认。
- Codex 只能静态标记“待确认”，不得写成既定事实。

## 7. stop.sh 分级停服策略（v1.2 新增）

- `stop.sh` 含 `kill -9` 强停风险，禁止作为默认第一动作。
- 建议分级停服：
  1. 优先使用温和停服策略（若服务支持，例如信号优雅退出/运维封装停服命令）。
  2. 必须先确认 PID 与进程归属，再执行 kill。
  3. `kill -9` 仅作最后兜底。
- 执行停服前必须保存日志与当前进程清单，便于回溯。
- Codex 不执行停服，仅做静态风险提示与流程建议。

## 8. 配置、数据库与网络检查（分工修订）

- 配置侧：`Config/*.xml` 与根目录 `*.xml`、`quest/`、`newquest/` 的路径与可读性（Codex可静态核对）。
- 数据库侧：连接参数来源、库名表名权威来源（配置文件/初始化 SQL/运维文档）需服务器侧验证。
- 网络侧：端口与拓扑在仓库中未完全固化，必须由运维基线文档与服务器侧实测补全。

## 9. 常见故障处理总则

1. 先定位阶段：依赖缺失 / base 编译 / ScenesServer 链接 / 启动后退出 / 登录失败。
2. 先查事实文件，再决定处理：`Makefile`、服务目录日志、`docs/rag_sources/10_已修复编译问题记录.md`。
3. `base` 与 `ScenesServer` 问题优先按附录B关键词表排查。
4. 若问题需要真实执行验证，立即切换到 Claw/SSH/人工流程。

## 11. 上线前检查（P0/P1 收口）

### P0（发布前必须确认）

1. 当前正式 OS 基线版本（CentOS 6.5 是历史基线还是现行基线）。
2. 生产端口号与完整拓扑（外网入口、内网互联、数据库访问域）。
3. `UserServer` 是否仍为部署必需组件。
4. 服务日志实际落盘目录（含 `/tmp/*.log*` 行为是否仍存在）。
5. 数据库库名/表名最终权威来源。
6. `gd` / `jpeg` 在当前构建链是否仍为必需。
7. 启动顺序最终采用 `start.sh` 还是 `start1.sh`。

### P1（v1.2 建议确认）

1. 部署态二进制目录与源码目录差异（`./SuperServer` vs `SuperServer/SuperServer`）。
2. `roleRegServer`、`InfoServer` 在现网是否仍保留。
3. 客户端/登录器联调中 `runtime_validation` 与 `launcher_reanalysis` 的优先级顺序。
4. shebang 异常脚本在目标服务器上的实际执行兼容方式。
