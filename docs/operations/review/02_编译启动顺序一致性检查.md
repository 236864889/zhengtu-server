# 编译与启动顺序一致性检查

## 对比基线
- 编译：`ztgame/Makefile` vs `docs/rag_sources/02_编译顺序与产物.md`
- 启动：`ztgame/start.sh`、`ztgame/start1.sh` vs `docs/rag_sources/03_服务端启动顺序.md`

## 编译顺序是否一致
- 结论：**基本一致**。
- 事实：`ztgame/Makefile` 的 `SUB_DIRS` 为
  `base/EncDec -> base -> MiniServer -> ScenesServer -> SessionServer -> BillServer -> GatewayServer -> SuperServer -> RecordServer -> FLServer -> tools`。
- `rag_sources/02` 将链路整理为“基础库 -> 服务端 -> tools”，并单独说明 `script` 非顶层 SUB_DIRS，但被服务端链接，表述与 Makefile 实际结构一致。

## 启动顺序是否一致
- 结论：**分支一致（脚本差异已在文档体现）**。
- `start.sh`：`Super -> Record -> Bill -> Mini -> Session -> Scenes -> Gateway`，`FL` 注释禁用。
- `start1.sh`：`Super -> FL -> Record -> Bill -> Mini -> Session -> Scenes -> Gateway`。
- `rag_sources/03` 同时记录上述两套顺序，并给出“实测/推荐链路”含 `UserServer` 的待确认说明。

## FLServer 是否默认启动
- 结论：**非统一默认**。
- 在 `start.sh` 中默认不启动（注释）；在 `start1.sh` 中默认启动。

## UserServer 是否存在
- 结论：**源码树内未见对应目录，当前为待确认组件**。
- 与 `rag_sources/03` 的“可能来自部署目录或历史组件”描述一致。

## stop.sh 是否存在 kill -9 风险
- 结论：**存在风险**。
- `stop.sh` 使用 `kill -9` 强制终止，且通过 `ps|grep` 粗筛 PID，存在误杀与日志未落盘风险。

## 手册建议表述
1. 启动顺序采用“双基线说明”：
   - 基线A：严格按 `start.sh`（不含 FL）。
   - 基线B：按 `start1.sh`（含 FL）。
2. 将 `UserServer` 标记为“部署环境确认项”，不得写成源码内必然步骤。
3. 对 `stop.sh` 增加高风险警示：生产先尝试温和停服，再兜底 `kill -9`。
4. 每一步增加“成功判定（进程/日志关键字）”。
